Three-Container Application

This application consists of an Nginx frontend, a Python backend REST API and a MySQL database. The application is deployed on CSC Rahti using Kubernetes.

1. Frontend → Backend → Database Communication

The frontend communicates with the Python backend using REST API requests. Nginx forwards requests beginning with /api to the backend service. The backend then communicates with the MySQL database. The database time and visit counter displayed above demonstrate communication between the frontend, backend and database.

2. Database Persistence

I tested database persistence by increasing the visit counter to 10. I then deleted the MySQL Pod. Kubernetes automatically created a new database Pod. After the new Pod started, the visit counter was still 10. This demonstrated that the database data persisted even when the database Pod was recreated.

3. Pod Recovery Experiment

I tested Kubernetes Pod recovery by deleting a running backend Pod. Kubernetes automatically created a replacement Pod because the Deployment required the specified number of replicas to remain running. This demonstrated the self-healing behaviour of Kubernetes.

Evidence

4. Scaling Experiment

I scaled the backend deployment from one replica to two replicas. Rahti created another backend Pod, and both backend Pods were running at the same time. This demonstrated how Kubernetes can scale an application by changing the number of replicas.

Evidence

5. Application Update

I modified the frontend application and pushed the changes to the GitHub repository. A new build was started in Rahti and a new container image was created successfully. Kubernetes then deployed the updated version of the application.

During the rollout, the new Pod replaced the previous application version while the Deployment continued managing the application.

6. Problems Encountered and Solutions

One of the main problems was communication between the frontend and backend. The frontend initially produced API errors because Nginx was not correctly forwarding API requests to the backend. I corrected the Nginx configuration so that requests to /api were forwarded to the backend service on port 8000.

I also encountered a browser caching problem. The updated application worked in Incognito mode but the normal browser continued showing an older version. Refreshing the browser and clearing the cached version solved this problem.

7. Rahti Compared with Docker Compose and cPouta

In the previous cPouta deployment, Docker Compose was used to start and manage the containers on a virtual machine. Networking and container configuration were mainly defined in the Docker Compose configuration.

In Rahti, the application is managed using Kubernetes resources such as Deployments, Services, Pods and Routes. Kubernetes also provides features such as automatic Pod recovery, scaling and rolling updates. This makes application management more automated compared with manually managing the containers on a cPouta virtual machine.
