Week 6 — Part A: CI/CD Pipeline

Objective

In Part A, I created a CI/CD workflow for the Flask backend of my existing cloud application. The purpose of the workflow is to automatically build the backend container image, push it to GitHub Container Registry and deploy the new image to CSC Rahti.

1. CI/CD Pipeline Overview

Continuous Integration and Continuous Deployment automate steps that would otherwise need to be performed manually after changing application code. In my implementation, a push to the GitHub repository starts a GitHub Actions workflow.

The workflow checks out the repository, builds the backend container image, logs in to GitHub Container Registry, pushes the image, installs the OpenShift command-line tool and then deploys the new backend image to Rahti.

Git Push → GitHub Actions → Build Container → GHCR → Rahti/OpenShift → Backend Pod

2. Container Image and Deployment

The backend container image is stored in GitHub Container Registry. The Rahti backend Deployment uses this image for the running backend containers.

This approach connects source-code changes in GitHub with the application running in Rahti. Instead of manually rebuilding and replacing the container after every change, the workflow performs these deployment operations automatically.

3. Authentication and Secrets

The workflow needs authentication to push the container image and communicate with Rahti. Authentication information should not be written directly into the workflow source code.

Sensitive values such as access tokens should be stored as GitHub Actions secrets. This prevents credentials from being exposed in the public repository.

4. Troubleshooting the CI/CD Pipeline

Problem encountered

Incorrect Rahti Project Name

During the first CI/CD attempt, the workflow successfully completed the image build and push steps, but the deployment step failed.

The workflow attempted to use the project cloudservice-week2, while the Rahti project available to my account was cloudservices-week2.

The error therefore occurred during the Deploy to Rahti stage rather than during the container build.

I corrected the project name in the workflow configuration and pushed the change again. After this correction, the GitHub Actions workflow completed successfully.

Week 6 — Part B: Health Checks and Logging

Objective

In Part B, I improved the reliability and observability of the backend deployment by configuring Kubernetes readiness and liveness probes and checking the backend application logs.

These features allow Kubernetes to determine whether the application is ready to receive traffic and whether the container is still functioning correctly.

1. Backend Health Endpoints

The backend provides dedicated health endpoints that can be called by Kubernetes/OpenShift.

Liveness endpoint: /healthz

Readiness endpoint: /readyz

Backend port: 8000

The liveness endpoint indicates whether the backend application process is alive. The readiness endpoint indicates whether the backend is ready to receive requests.

2. Readiness Probe

The readiness probe performs an HTTP request to /readyz on port 8000.

My deployment configuration uses an initial delay before the checks begin and then performs the readiness check periodically. If the readiness probe fails, Kubernetes can temporarily stop directing normal service traffic to that pod.

3. Liveness Probe

The liveness probe performs an HTTP request to /healthz on port 8000.

The liveness probe is useful for detecting a container that is still running at the process level but whose application is no longer responding correctly. Repeated liveness failures can cause Kubernetes to restart the container.

5. Rolling Deployment and Pod Readiness

Updating a Kubernetes Deployment can create a new ReplicaSet and new pods. During the rollout, old and new backend pods can temporarily exist at the same time.

A newly created pod may initially show 0/1 in the Ready column. After the readiness check succeeds, it changes to 1/1.

6. Application Logging

Logging provides information about requests received by the backend and is important when troubleshooting an application running inside containers.

I inspected the backend pod logs in Rahti. The logs show HTTP requests made automatically to the health endpoints.

Evidence B5

7. Why Health Checks Matter

Readiness

A running container is not necessarily ready to serve users. A readiness probe allows Kubernetes to determine whether the application should currently receive service traffic.

Liveness

A process can continue running even when the application has stopped behaving correctly. A liveness probe provides a mechanism for detecting this situation.

Logging

Logs make application behaviour visible and provide useful information when diagnosing failures, HTTP errors and health-check problems.
