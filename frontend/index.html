Part A - Questions

1. SAML and OAuth

SAML (Security Assertion Markup Language) and OAuth are both used in identity and access systems, but they solve different problems. SAML is mainly used for authentication and Single Sign-On (SSO). It allows a user to authenticate with an Identity Provider and then access another application, called the Service Provider, without signing in again.

For example, a company could use SAML so that employees sign in with their company account and then access several internal applications without entering a separate username and password for every application.

OAuth, on the other hand, is mainly an authorization framework. It allows an application to receive limited permission to access another service on behalf of a user without receiving the user's password. OAuth commonly uses access tokens for this purpose.

For example, an application could request permission to access some information from a user's Google account. The user gives permission through Google and the application receives an access token instead of the user's Google password.

A company would therefore commonly choose SAML when it needs enterprise Single Sign-On between an identity provider and its applications. OAuth is more suitable when an application needs delegated access to another service or API. For authentication based on OAuth technology, OpenID Connect can be used on top of OAuth 2.0.

2. Web Application Firewall (WAF)

A Web Application Firewall, or WAF, is a security system that monitors and filters HTTP and HTTPS traffic going to a web application. Unlike a traditional network firewall that mainly works with network addresses, ports and protocols, a WAF can inspect web requests at the application layer.

A WAF can help protect a web application from common attacks such as SQL injection and cross-site scripting (XSS). It can inspect incoming requests and block requests that match suspicious or malicious patterns before they reach the application.

In the Week 4 architecture, the application flow was:

Route → Nginx Frontend → Flask Backend → MySQL Database

I would place the WAF in front of the publicly accessible web application, before requests reach the frontend/backend application services. This would allow suspicious HTTP requests to be filtered before they reach the internal application components.

The database and internal services should not be directly exposed to the Internet. This same idea is relevant to the Redis extension in Part B: Redis should remain an internal service rather than being exposed using a public Route.

3. Decentralized Storage vs Centralized Object Storage

Centralized object storage services such as CSC Allas or Amazon S3 are managed storage systems where users upload objects to storage infrastructure operated by a provider. Applications normally communicate with the provider through an API or other supported interface.

A decentralized or cooperative storage network works differently. Data can be distributed between multiple participating nodes rather than depending on one central storage provider. Systems such as IPFS can also use content-based addressing, where content can be identified based on its data rather than only by a traditional server location.

One advantage of decentralized storage is that data can be distributed across multiple nodes, which can reduce dependence on a single provider or location. It can also provide redundancy when content is available from multiple nodes.

However, decentralized storage can introduce additional challenges. Availability may depend on whether data is replicated or pinned by participating nodes. Performance can be less predictable, and access control, privacy, deletion and management may be more complicated.

Centralized object storage is usually easier for an organization to manage because the provider offers a defined service, permissions, APIs and operational tools. In this course I used CSC Allas to store public screenshots for my documentation, which is a practical example of centralized object storage.

4. YAML and JSON

YAML is a human-readable data serialization format that is commonly used for configuration files. Kubernetes and OpenShift/Rahti commonly use YAML manifests to describe resources such as Deployments, Services, ConfigMaps, Secrets and PersistentVolumeClaims.

YAML works well for Kubernetes configuration because a large amount of structured configuration can be written in a format that is relatively easy for people to read and edit. Indentation represents structure, so related configuration can be grouped clearly.

JSON can represent the same type of structured information, but it uses braces, brackets, commas and quotation marks more explicitly. JSON is widely used for APIs and communication between applications, while YAML is often more convenient for configuration files that people need to edit manually.

One disadvantage of YAML is that indentation is important. Incorrect indentation can change the structure of a document or make a manifest invalid. JSON is usually more verbose, but its syntax makes the structure very explicit.

In my Rahti work I used YAML-style Kubernetes/OpenShift resource definitions for components such as Deployments, Services and ConfigMaps. This made it possible to describe the desired application configuration in a structured way.

Part B - Hands-On: Redis Cache Extension

In Week 4 I deployed a three-container application consisting of an Nginx frontend, Flask/Gunicorn backend and MySQL database in CSC Rahti. For Week 5 I selected Option 2: Add a Redis Cache.

Redis was added as a fourth application component with its own Deployment and Kubernetes Service. The purpose was to extend the existing orchestrated application while keeping the original frontend → backend → database functionality working.

1. Updated Application Architecture

The Week 4 architecture was extended by adding Redis. The user accesses the application through the Rahti Route. Nginx serves the frontend and forwards API requests to the Flask/Gunicorn backend.

The backend communicates with MySQL for persistent application data and Redis for cached data. Kubernetes Services provide internal communication between these components.

Figure 1: Updated Week 5 application architecture showing Redis as the fourth component.

2. Redis Cache Implementation

Redis was deployed as a separate component in the Rahti OpenShift environment. It has its own Deployment and Service instead of being installed inside the existing Flask container.

The Redis component is used as an in-memory cache. The Flask backend can store a value in Redis and retrieve the cached value in later requests.

This demonstrates the same Deployment and Service pattern that was used for the other components of the application. Redis runs independently while communicating with the backend through the internal cluster network.

3. Redis Configuration and Communication

Redis has its own Kubernetes Service. The Flask backend communicates with Redis through the internal service name redis on port 6379.

The backend receives the Redis connection information through environment configuration. In my deployment I used REDIS_HOST=redis and REDIS_APP_PORT=6379.

Using the Kubernetes Service name means that the backend does not need to know the IP address of the Redis pod. Kubernetes service discovery provides a stable service name even if the Redis pod is recreated and receives a different IP address.

Redis is used internally by the application and is not exposed through a public Route. Sensitive credentials should be stored in Kubernetes Secrets and should never be committed to Git or displayed in screenshots. The existing MySQL application also uses ConfigMaps and Secrets for configuration and credentials.

5. Production Readiness, Security and Reliability

If this application were used in production, cache invalidation would be an important reliability concern. Information stored in Redis can become outdated when the original data changes.

To reduce this problem, cached values should have an appropriate expiration time, also known as a TTL. The application should also remove or update cached values when the original information changes. This helps prevent users from receiving stale information from the cache.

Redis should remain an internal service and should not be exposed directly to the public Internet through a Route. If authentication information or passwords are required, they should be stored in Kubernetes Secrets rather than written directly into source code or committed to Git.

In a production environment I would also use health checks, monitoring and suitable CPU and memory resource limits. The backend should handle a temporary Redis failure safely instead of allowing a cache failure to make the whole application unavailable.

Connection to Part A

This also connects to my WAF answer in Part A. A WAF would be placed in front of the publicly accessible web application to inspect and filter HTTP/HTTPS traffic. Internal components such as MySQL and Redis should not be directly exposed to the Internet.

Together, these controls provide different layers of protection. The WAF helps protect the public web application from malicious web requests, while Kubernetes Services, Secrets and internal networking help protect and configure the application's internal components.

6. Problems Encountered and Solutions

Problem 1 - Redis Port Environment Variable

When I first connected the Flask backend to Redis, the backend container failed to start correctly. The Redis port environment variable contained a value similar to tcp://...:6379, while the Python application expected only a numeric port.

I solved this by using a separate environment variable, REDIS_APP_PORT=6379. After this change, the backend started successfully and the Redis ping returned True.

Problem 2 - Frontend API Request

The frontend initially received an HTML error page instead of JSON. This resulted in an error similar to Unexpected token '<'.

The frontend was requesting /api, while the Nginx proxy configuration handled requests under /api/. I corrected the frontend request to use the proper endpoint /api/status.

After this change, the frontend successfully displayed the database connection status, database time and visit counter.

Problem 3 - Build Resource Quota

During deployment, one of the builds could not create its build pod because the project's CPU resource quota had been reached.

I checked the build status and existing resources and retried the deployment after resources became available. After resolving the resource issue, the build completed and the application could be deployed successfully.
